  - โดเมนโมเดลและสถานะกลาง: **`MD-DOM-04`** (`Saleng`: `salengId`, `phone`, `displayName`, `verified`, `kycStatus`, `vehicleType`, `maxCapacityKg`, `currentLocation`) ([`specs/000-shared/constraints.md`](../../000-shared/constraints.md), [`specs/002-route/models.md`](../../002-route/models.md))
  - ความต้องการที่เกี่ยวข้อง:
    - **`UC-01`**: ระบบบัญชีและการยืนยันตัวตนผู้รับซื้อ (ซาเล้ง)
    - **`REQ-FN-001`**: จัดการข้อมูลยานพาหนะและควบคุมน้ำหนักบรรทุกสูงสุดของรถซาเล้ง (`maxCapacityKg` ตามกฎ `BR-03`)
    - **`REQ-SEC-001`**: บันทึก Audit Log ทุกเหตุการณ์การสมัคร, เข้าสู่ระบบ, ส่งเอกสาร KYC, และการอนุมัติ/ปฏิเสธแบบ Append-only
    - **`REQ-SEC-002`**: ปกปิดเบอร์โทรศัพท์เป็น `08X-XXX-XXXX` (PDPA Masking) และคุ้มครองข้อมูลบัตรประชาชน
    - **`REQ-UX-001`**: หน้าจอบนมือถือสำหรับซาเล้งใช้งานกลางแจ้ง ปุ่มสูงไม่น้อยกว่า `48px`
    - **`REQ-QA-001`**: การตอบสนองของการเข้าสู่ระบบและตรวจสอบสถานะ KYC ต้องไม่เกิน `2.0 วินาที` (P95)
    - **`REQ-OP-001` / `CC-05`**: การเก็บรักษาเซสชัน Token และแคชข้อมูลโปรไฟล์ซาเล้งใน `localStorage` รองรับการเปิดดูออฟไลน์

> [!NOTE]
> **ความสอดคล้องกับสารบัญกลางและสถาปัตยกรรมระบบ (`CC-01`, `CC-02`, `CC-03`):**
> 1. **`CC-01` (Requirements Catalogue Alignment):** ปลดรหัส `REQ-CON-003` ที่อยู่นอกสารบัญความต้องการกลาง และเชื่อมโยงรหัสกลาง **`REQ-FN-001`** (การควบคุมความจุน้ำหนักรถ), **`REQ-SEC-001`** (Audit Log), **`REQ-SEC-002`** (PDPA Masking), **`REQ-QA-001`** (< 2.0s), กฎธุรกิจ **`BR-03`**, และข้อจำกัดกลาง **`D-00-01`**
> 2. **`CC-02` (AC ID Structure):** ปรับรหัสเกณฑ์การยอมรับให้เป็นมาตรฐานเฉพาะของฟีเจอร์คือ **`AC-B01-01` ถึง `AC-B01-05`** แทนการอ้างอิงข้าม Use Case ไปยัง `AC-04-08`
> 3. **`CC-03` (Precondition Enforcement):** สถานะ `verified = true` เป็นเงื่อนไขบังคับก่อนเริ่ม (**Precondition Gate**) ของการกดรับงานใน `UC-04` หากซาเล้งยังไม่ผ่าน KYC ระบบต้องล็อกปุ่มรับงานและแจ้งเตือนทันที

## 1. ขอบเขตการทำงาน (Feature Scope)

1. **สมัครสมาชิกและเข้าสู่ระบบด้วยเบอร์โทรศัพท์และ OTP (`Collector Phone Registration & OTP Login` — `UC-01`, `REQ-UX-001`, `REQ-QA-001`, `Q-01`):**
   - ซาเล้ง (`Collector / Saleng`) กรอกเบอร์โทรศัพท์มือถือ (10 หลัก) เพื่อขอรับรหัส OTP 6 หลัก
   - ระบบส่งรหัส OTP (ในสภาพแวดล้อมทดสอบจำลองรหัส OTP เช่น `123456`)
   - เมื่อซาเล้งกรอกรหัส OTP ถูกต้อง:
     1. หากเป็นเบอร์ใหม่: ระบบสร้างบัญชีซาเล้งใหม่ กำหนดสถานะ KYC เริ่มต้นเป็น `UNVERIFIED` และ `verified = false`
     2. หากเป็นเบอร์เดิม: ระบบดึงข้อมูลโปรไฟล์ ประเภทยานพาหนะ และสถานะ KYC เดิมขึ้นมาใช้งานทันที
     3. ออกเซสชันโทเคน (`session_token`) พร้อมเวลาหมดอายุ ส่งกลับภายใน `< 2.0 วินาที` (`REQ-QA-001`)
   - ซาเล้งสามารถแก้ไขชื่อที่แสดง (`displayName`) ในหน้าโปรไฟล์ได้

2. **การตั้งค่าประเภทยานพาหนะและความจุรถ (`Vehicle Profile & Capacity Setup` — `REQ-FN-001`, `MD-DOM-04`, `Q-04`):**
   - ซาเล้งสามารถเลือกประเภทยานพาหนะรับซื้อของเก่าจาก 3 มาตรฐานหลัก:
     1. **`TRICYCLE` (ซาเล้งสามล้อถีบ):** ความจุน้ำหนักบรรทุกเริ่มต้น `150.0 กก.`
     2. **`SIDE_CAR_MOTORCYCLE` (ซาเล้งพ่วงข้างมอเตอร์ไซค์):** ความจุน้ำหนักบรรทุกเริ่มต้น `300.0 กก.`
     3. **`PICKUP_TRUCK` (รถกระบะรับซื้อของเก่า):** ความจุน้ำหนักบรรทุกเริ่มต้น `1,000.0 กก.`
   - ซาเล้งสามารถปรับแต่งตัวเลขน้ำหนักบรรทุกสูงสุดจริง (`max_capacity_kg`) และระบุหมายเลขทะเบียนรถ (`license_plate`) ได้
   - ข้อมูลความจุรถนี้จะถูกนำไปใช้ใน `UC-04` สำหรับการควบคุมไม่ให้น้ำหนักของเก่าที่รับสะสมเกินความจุรถตามกฎ `BR-03`

3. **การส่งเอกสารยืนยันตัวตน Thai-ID / DBD-ID (`KYC Document Submission` — `SC-04`, `REQ-QA-001`, `Q-02`):**
   - ซาเล้งส่งเอกสารเพื่อขอรับการยืนยันตัวตน ประกอบด้วย:
     1. หมายเลขบัตรประชาชน 13 หลัก (`id_card_no`) หรือเลขทะเบียนนิติบุคคล DBD
     2. ชื่อ-นามสกุลตามบัตรประชาชน (`full_name`)
     3. ภาพถ่ายหน้าบัตรประชาชน (`id_card_photo_url`)
     4. ภาพถ่ายหน้าตรงถือบัตรประชาชน (`selfie_photo_url`)
     5. ภาพถ่ายยานพาหนะพร้อมป้ายทะเบียน (`vehicle_photo_url`)
   - เมื่อส่งเอกสารสำเร็จ สถานะ KYC ของซาเล้งจะเปลี่ยนจาก `UNVERIFIED` เป็น **`PENDING_REVIEW`**

4. **วงจรสถานะการตรวจสอบ KYC 4 สถานะ (`KYC Status Lifecycle` — `MD-DOM-04`, `D-00-01`, `Q-03`):**
   - **`UNVERIFIED`**: เพิ่งสมัครสมาชิก ยังไม่ได้ส่งเอกสาร KYC (`verified = false`)
   - **`PENDING_REVIEW`**: ส่งเอกสารครบถ้วนแล้ว อยู่ระหว่างการรอแอดมินหรือระบบตรวจสอบ (`verified = false`)
   - **`VERIFIED`**: ผ่านการตรวจสอบและอนุมัติแล้ว 100% (`verified = true`, มีป้าย "ยืนยันตัวตนแล้ว" สีฟ้า/เขียว)
   - **`REJECTED`**: เอกสารไม่ผ่านการอนุมัติ (เช่น ภาพไม่ชัด ข้อมูลไม่ตรง) มีข้อความระบุเหตุผล (`rejection_reason`) และเปิดโอกาสให้ซาเล้งแก้ไขส่งเอกสารใหม่ได้

5. **การบล็อกการรับงานสำหรับซาเล้งที่ยังไม่ Verify (`Unverified Collector Gate` — `D-00-01`, `Q-05`):**
   - ซาเล้งที่ยังไม่อนุมัติ (`verified = false` ในสถานะ `UNVERIFIED`, `PENDING_REVIEW`, หรือ `REJECTED`) สามารถเปิดดูแอปพลิเคชัน ดูโปรไฟล์ และเปิดดูแผนที่รายการขยะในพื้นที่ได้
   - แต่เมื่อพยายามกดปุ่ม **"รับงาน (Claim / Accept Job)"** ในระบบ `UC-04`:
     - ระบบต้องบล็อกการดำเนินการทันที และโยน `HTTP 403 Forbidden` พร้อมข้อความแจ้งเตือน: *"กรุณายืนยันตัวตนผ่าน Thai-ID / DBD-ID ให้สำเร็จก่อนกดรับงานตามกฎความปลอดภัย D-00-01"*
     - หน้าจอ UI จะปิดการทำงานปุ่มรับงาน (Disabled) พร้อมแสดง Modal แนะนำให้ไปหน้าส่งเอกสาร KYC

6. **ระบบจำลองการอนุมัติ KYC สำหรับการทดสอบ (`Mock KYC Admin Approval Endpoint` — `Q-06`):**
   - เปิด Endpoint เฉพาะสำหรับสภาพแวดล้อม Development / Automated Test:
     - `POST /api/v1/collectors/{id}/mock-kyc-approval` ➔ เปลี่ยนสถานะเป็น `VERIFIED` และ `verified = true` ทันที
     - `POST /api/v1/collectors/{id}/mock-kyc-rejection` ➔ เปลี่ยนสถานะเป็น `REJECTED` พร้อมบันทึกเหตุผล
   - ช่วยให้ชุดทดสอบ Pytest, Vitest และ UAT ทำงานได้อย่างอิสระโดยไม่ต้องรอระบบแอดมินจริง

7. **การบันทึกประวัติด้านความปลอดภัยและการตรวจสอบ (`Security Audit Logging` — `REQ-SEC-001`, `EV-08`):**
   - ทุกธุรกรรมต้องบันทึกลงในตาราง `AuditLog` แบบ Append-only:
     1. การส่ง OTP ซาเล้ง (`COLLECTOR_OTP_REQUESTED`)
     2. การเข้าสู่ระบบสำเร็จ (`COLLECTOR_LOGIN_SUCCESS`)
     3. การอัปเดตข้อมูลยานพาหนะ (`COLLECTOR_VEHICLE_UPDATED`)
     4. การส่งเอกสาร KYC (`COLLECTOR_KYC_SUBMITTED`)
     5. การอนุมัติ KYC (`COLLECTOR_KYC_APPROVED`)
     6. การปฏิเสธ KYC (`COLLECTOR_KYC_REJECTED`)

## 2. ขอบเขตและสิ่งที่ไม่ทำในรอบนี้ (Non-goals)

1. **ไม่เชื่อมต่อระบบตรวจสอบใบขับขี่หรือฐานข้อมูลกรมการปกครองแบบ Live Real-time API:** ใช้กระบวนการตรวจสอบเอกสารและภาพถ่ายผ่านแอดมิน Gatekeeper ร่วมกับ Mock Approval เพื่อความคล่องตัวในการทดสอบ
2. **ไม่ทำระบบกู้คืนรหัสผ่านด้วยอีเมล:** ซาเล้งใช้งานด้วยเบอร์โทรศัพท์มือถือและ Phone OTP 100%
3. **ไม่ทำระบบตัดแต้มความประพฤติในโมดูลนี้:** ระบบตัดคะแนนและการระงับบัญชีถูกแยกไปอยู่ใน `specs/admin/01-user-verification-and-penalty/`
4. **ไม่รับชำระค่าธรรมเนียมสมัครสมาชิก:** ซาเล้งสมัครสมาชิกและยืนยันตัวตนฟรี ไม่มีค่าใช้จ่าย

## 3. เกณฑ์การยอมรับ (`Acceptance Criteria`)

- **`AC-B01-01` (Collector Phone Registration & Session Persistence):**
  - ซาเล้งสามารถกรอกเบอร์โทรศัพท์เพื่อขอรับ OTP และยืนยันรหัส OTP เพื่อเข้าสู่ระบบได้ภายใน `< 2.0 วินาที` (`REQ-QA-001`)
  - ระบบออก `session_token` จัดเก็บลงใน `localStorage` เพื่อให้คงสภาพการเข้าสู่ระบบไว้ได้เมื่อเปิดแอปใหม่ (`CC-05`, `REQ-OP-001`)
  - เบอร์โทรศัพท์ที่แสดงบนหน้าจอโปรไฟล์ต้องถูก Masking ตามกฎ PDPA เป็น `08X-XXX-XXXX` (`REQ-SEC-002`)
- **`AC-B01-02` (Vehicle Profile & Capacity Setup):**
  - ซาเล้งสามารถเลือกประเภทยานพาหนะจาก 3 มาตรฐาน (`TRICYCLE` 150 กก., `SIDE_CAR_MOTORCYCLE` 300 กก., `PICKUP_TRUCK` 1,000 กก.) และระบุเลขทะเบียนรถได้
  - ซาเล้งสามารถปรับแต่งค่าน้ำหนักบรรทุกสูงสุด (`max_capacity_kg`) ให้ตรงกับสภาพรถจริงได้
- **`AC-B01-03` (Thai-ID / DBD-ID KYC Submission & Lifecycle Status):**
  - ซาเล้งสามารถกรอกเลขบัตรประชาชน 13 หลัก แนบภาพหน้าบัตร ภาพหน้าตรงถือบัตร และภาพถ่ายรถ เพื่อส่งคำขอ KYC
  - คำขอที่ส่งสำเร็จต้องมีสถานะเป็น `PENDING_REVIEW`
  - เมื่อได้รับการอนุมัติ สถานะต้องเปลี่ยนเป็น `VERIFIED` พร้อมตั้งค่า `verified = true` และแสดงป้าย "✓ ยืนยันตัวตนแล้ว 100%"
  - หากถูกปฏิเสธ สถานะต้องเป็น `REJECTED` พร้อมแสดงเหตุผลและปุ่มให้ส่งเอกสารแก้ไขใหม่ได้
- **`AC-B01-04` (Unverified Collector Job Claim Block Gate):**
  - หากบัญชีซาเล้งยังไม่อนุมัติ (`verified = false`) เมื่อพยายามกดรับงาน ระบบ API ต้องบล็อกด้วย `HTTP 403 Forbidden` ทันทีตามกฎ `D-00-01`
  - หน้าจอ UI ต้องปิดการทำงานปุ่มรับงาน และแสดงหน้าต่างแจ้งเตือนให้ไปยืนยันตัวตน
- **`AC-B01-05` (Security Audit Logging for Collector Accounts):**
  - ทุกการส่งคำขอ OTP, การเข้าสู่ระบบ, การบันทึกยานพาหนะ, การส่งเอกสาร KYC, และผลการอนุมัติ/ปฏิเสธ ต้องบันทึกลงในตาราง `AuditLog` ครบถ้วน (`REQ-SEC-001`)

| **`Q-01`** | วิธีการเข้าสู่ระบบของซาเล้ง | ใช้เบอร์โทรศัพท์และรหัส OTP 6 หลัก (`Phone OTP`) พร้อมออก Session Token | เหมาะกับซาเล้ง ไม่ต้องจำรหัสผ่าน สอดคล้องกับฝั่งผู้ขายและ `CC-01` |
| **`Q-02`** | เอกสารที่ต้องใช้ยืนยันตัวตน KYC | เลขบัตร ปชช. 13 หลัก, ภาพถ่ายหน้าบัตร, ภาพถ่ายหน้าตรงถือบัตร, และภาพถ่ายรถ | ครบถ้วนตามมาตรฐาน `SC-04` และป้องกันการสวมสิทธิ์ซาเล้ง |
| **`Q-03`** | วงจรสถานะการตรวจสอบ KYC | กำหนด 4 สถานะ: `UNVERIFIED`, `PENDING_REVIEW`, `VERIFIED`, `REJECTED` | ทำให้ซาเล้งติดตามความคืบหน้าได้ชัดเจน และแก้ไขเอกสารได้หากไม่ผ่าน |
| **`Q-04`** | ประเภทยานพาหนะและความจุเริ่มต้น | 3 มาตรฐาน: `TRICYCLE` (150 กก.), `SIDE_CAR_MOTORCYCLE` (300 กก.), `PICKUP_TRUCK` (1,000 กก.) | ตรงตามความเป็นจริงของซาเล้งไทย และเตรียมส่งต่อให้ `UC-04` คุมโควตารถ |
| **`Q-05`** | พฤติกรรมการบล็อกเมื่อยังไม่ Verify | เข้าดูแอปและแผนที่ได้ แต่ล็อกปุ่ม "กดรับงาน" (`HTTP 403`) ตามกฎ `D-00-01` | ให้ซาเล้งเห็นงานในพื้นที่เพื่อกระตุ้นให้รีบส่งเอกสารยืนยันตัวตน |
| **`Q-06`** | การจำลองการอนุมัติเพื่อทดสอบ | สร้าง Mock Approval/Rejection Endpoints สำหรับ Dev/Test | ช่วยให้สามารถรัน Automated Test และ UAT ได้โดยไม่ต้องพึ่งพาแอดมินจริง |
